## Reconnecting, step by step

```text
client: {"type":"join","doc":"demo","replica":"k3j9x2","name":"Ann","lastSeq":41}
server: {"type":"remote","ops":[{"seq":42,...},{"seq":43,...}]}   only what was missed
server: {"type":"joined","doc":"demo","seq":43,"you":{"replica":"k3j9x2","name":"Ann","color":"#2f6fde"}}
```

## Key ideas

- **Send only what was missed.** A reconnecting client says which sequence number it has. The server pages through history after that point.
- **Identity without accounts.** Every visitor is a guest, known by the replica name its CRDT puts in op IDs, plus a cleaned-up display name. The colour comes from a hash of the replica name, so it stays the same across reconnects without storing anything.
- **No forged edits.** A connection may only send ops made by its own replica. Anything else is refused and the connection closed.
- **Persistence is proven by restarting.** A new service process rebuilds each document from PostgreSQL and carries on with the next sequence number.
- **An unsaved edit must be forgotten.** If storing fails, the CRDT drops what it applied and rebuilds from the database. Otherwise a retry would look like a duplicate and the edit would never be saved.
- **Fail loudly.** If `DATABASE_URL` is set but unreachable, the gateway refuses to start rather than quietly keeping documents in memory.
