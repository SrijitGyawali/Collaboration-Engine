## What happens when the connection drops

```text
typing ─▶ ops go into the unacked queue ─▶ sent ─▶ ack removes them
connection drops ─▶ "offline, reconnecting… (your edits are kept)"
typing continues ─▶ ops queue up locally
retry after 0.5 s, 1 s, 2 s … (up to 10 s, with jitter)
join with lastSeq ─▶ server sends what was missed ─▶ joined
whole unacked queue is resent ─▶ duplicates acked as duplicates, new ones stored
```

## Key ideas

- **Nothing typed is lost.** An edit stays queued until the server acknowledges it, and the whole queue is resent after every reconnect. That is safe because the server answers anything it already has as a duplicate.
- **Why not the highest seq seen.** Broadcasts can overtake each other. A client that saw seq 6 but not seq 5 must ask for "after 4", not "after 6". `SeqTracker` keeps the highest number with no gaps.
- **Back off with jitter.** If the gateway restarts, a thousand clients retrying at the same instant would knock it over again.
- **Some refusals are final.** If the server closes with "policy violation" (for example an invalid replica name), retrying cannot help, so the client stops.
- **Same interface, different transport.** `CollabSession` and the editor binding did not change; only the transport underneath did.
- **`NEXT_PUBLIC_` variables are fixed at build time.** Next.js inlines them only when written out in full.

## Known limits

- The unacked queue lives in memory: closing the tab while offline loses those edits. IndexedDB comes on Nov 18.
- One gateway only. A second gateway's clients would not see the first one's broadcasts until Redis fan-out (Nov 15).
