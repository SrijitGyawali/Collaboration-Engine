## Key ideas

- **Editors speak positions, the CRDT speaks IDs.** `InsertAt(5, 'x')` looks up the character at position 4 and inserts after it by ID. The op on the network never contains a position.
- **For remote edits, the translation runs the other way.** After applying a remote op, `PositionOf` tells the editor where it landed. For a delete, the tombstone still reports where the character was.
- **Flat list instead of a tree.** The text is now stored in reading order. To place a new character: start after its parent, skip every character with a higher ID, and stop at the first lower one. This gives the same order as the tree, because a character is always newer than its parent. `order.go` explains why.
- **Rewriting safely.** First an independent reference model was added, computing the order from scratch with no shared code. Then the storage was rewritten. All 400 property sessions and every fuzz target compared the new storage with the reference model.
- **Measure, then fix.** The first version of the rewrite was correct but slow: finding a parent meant scanning the list, so typing 200,000 characters took 76 s. Remembering where the last insert happened brought that down to 0.09 s.

## Benchmarks (10,000 characters, this machine)

| Operation | Cost |
| --- | --- |
| Type at the end (`InsertAt(Len())`) | about 0.5 µs, 1 allocation |
| Type in the middle | about 6 to 15 µs |
| Backspace at the end | about 10 µs; grows with tombstones at the end |
| Position lookup in the middle (`IDAt`) | about 8 to 9 µs, no allocation |
| Render the text (`Text`) | about 0.12 ms (0.87 ms with the tree) |
| Apply 10,000 ops in order | about 4 to 5 ms (9 to 15 ms with the tree) |

All of these are far below what a person notices per keystroke (about 16 ms).

## Known limits

- Position lookups are O(n) scans. Very large documents would need an index, such as a balanced tree with visible counts per node.
- Tombstones are never removed, so a heavily edited document keeps growing. Compaction inside snapshots is later work.
