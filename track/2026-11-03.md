## Key ideas

- **Why duplicates happen.** Clients retry when an ack is lost, the server echoes a user's own op back, and Redis and Kafka deliver at least once. So a repeat must be a silent no-op, not an error.
- **Duplicate versus conflict.** The same ID with the same content is a repeat (`Duplicate`). The same ID with different content can only be corruption, so it is rejected.
- **Why ops arrive early.** Reconnects replay offline queues, two gateways forward at different speeds, and Kafka orders only within a partition.
- **One dependency per op.** An insert needs its parent and a delete needs its target. An early op waits for exactly that one character. When the character is inserted, everything waiting on it is applied, then everything waiting on those, and so on (a cascade).
- **Local and remote edits differ.** A user can only type next to characters they see, so a local edit of an unknown character is a bug and fails. Only remote ops wait.
- **The buffer needs a limit.** A client that sends ops whose parents never arrive could otherwise fill the server's memory.
- **Status matters for the server.** On Nov 10 the sync service will give a new op a sequence number, answer a `Duplicate` with its original ack, and not ack a `Pending` op until it is applied.

## Benchmarks

Today's timings were noisy: unchanged code ran about 3× slower than yesterday. So only the comparison within one run counts: receiving 10,000 ops backwards costs about 2.5 to 3× receiving them in order. That is the price of buffering each op once.
