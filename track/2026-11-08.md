## What one append does

```text
BEGIN
  SELECT ... FROM documents WHERE id = $1 FOR UPDATE     -- one writer per document
  SELECT op_id, seq FROM operations WHERE op_id = ANY(.) -- which of these are retries?
  SELECT COALESCE(MAX(seq), 0) ...                       -- where history ends
  INSERT INTO operations ...  and  INSERT INTO outbox ...-- one of each per new op
COMMIT
```

## Key ideas

- **Why a row lock.** Two writers reading `MAX(seq)` at once would pick the same number. Locking the document's row makes writers to one document take turns, and other documents are not affected.
- **Why not a database sequence.** A sequence leaves gaps after a rollback. Clients will treat a gap as a missed operation, so history must have none.
- **Retries get the original answer.** If a client lost its ack and sends the op again, it receives the same sequence number, marked as a duplicate.
- **The transactional outbox.** Writing to PostgreSQL and Kafka separately can leave them disagreeing if the process dies in between. So the event is saved in the same transaction as the edit, and a relay publishes it later.
- **Real database in tests.** Locks, constraints and rollbacks are exactly what a mock would get wrong.
- **Migrations are not edited once in the repo.** They may already be applied somewhere, so the ID type change is a new migration.
