## The problem

Until today a gateway only knew about edits sent through itself. With two gateways, Alice (on gateway A) and Bob (on gateway B) would each see only their own gateway's edits, until they reconnected and caught up from history.

## How an edit travels now

```text
alice ──ops──▶ gateway A ──gRPC──▶ sync service ──store──▶ PostgreSQL
                                        │
                                   PUBLISH collab:doc:<id>:ops
                                        ▼
                                      Redis
                              ┌─────────┴─────────┐
                              ▼                   ▼
                          gateway A           gateway B
                       (skips alice)        (sends to bob)
```

- **The sync service publishes, not the gateway.** It is the only writer, so it knows exactly which ops are new (duplicates and rejected ops are never published) and their sequence numbers. One message per run of ops by the same author.
- **One subscription per open document per gateway.** The first client to open a document on a gateway subscribes; the last one to leave unsubscribes. Clients of the same document share it.
- **Subscribe before reading history.** A joining client is put in the room and the subscription is confirmed by Redis before the gateway reads history. Anything committed after that arrives live; anything before is in history. Some ops may arrive both ways, and clients ignore what they already have.
- **The author is skipped by replica name.** The author already has an ack with the sequence numbers, so it is not sent its own edit back.
- **Publishing is best effort.** A failed publish is logged and never fails the edit: the edit is already stored, and other clients get it from history when they reconnect.

## Key ideas

- **Wait for Redis to confirm.** `SUBSCRIBE` is asynchronous. Without waiting for Redis's confirmation, an edit published just after subscribing could reach Redis first and be lost.
- **A second join waits for the first one's subscription.** If two clients open the same document at the same moment, the second must not read history before the subscription exists. A test holds the subscription open and checks that no history is read until it is live.
- **Fail loudly on misconfiguration.** If `REDIS_ADDR` is set and Redis does not answer, the binary refuses to start. Leaving it empty keeps the single-gateway setup working and logs a warning, because silently broadcasting only locally would split two gateways' editors into groups that can't see each other.
- **An in-memory broker for tests.** It behaves like Redis but delivers synchronously, so the tests are exact. It also lets tests run several gateways inside one process.

## Checks

- pubsub: memory broker tests always run; Redis tests run against a real Redis 8 container.
- syncsvc: stored ops are published, one message per author, rejected ops are not, and a failed publish does not fail the edit.
- gateway: two gateways over one in-memory broker. Edits cross gateways with their sequence numbers, the author gets no echo, a late joiner gets history and then live edits, subscriptions are released when rooms empty, concurrent joins share one subscription, and a failed subscription asks the client to retry. Repeated 5 times under the race detector.
- Stack: rebuilt with `make stack`. Both services log that they found Redis, and the browser end-to-end tests pass through the gateway, with every edit now coming back through Redis.
