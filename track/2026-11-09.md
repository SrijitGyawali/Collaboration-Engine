## How an edit flows now

```text
browser ──{"type":"ops"}──▶ gateway connection
                              └─ Backend.Apply ─▶ document actor (one goroutine per doc)
                                                    ├─ CRDT: validate and apply
                                                    └─ store: assign seq, save
browser ◀──{"type":"ack"}──── gateway ◀────────────── acks
other tabs ◀──{"type":"remote", seq}── room broadcast (new ops only)
```

## Key ideas

- **One goroutine per document.** All writes to a document pass through its actor, one at a time, so the CRDT needs no locks and every edit is stored in a single order. Different documents run in parallel.
- **Actors come and go.** A document's actor starts on first use (rebuilding the CRDT from stored history) and stops after 5 idle minutes.
- **Join the room before reading history.** Otherwise an edit committed in between would be missed. An edit seen twice is harmless.
- **Slow clients do not slow everyone.** Each client has its own queue and writer goroutine. A client that falls behind is disconnected and catches up when it reconnects.
- **Bad edits are rejected one by one.** A malformed or conflicting op gets an error in its ack; the rest of the batch still goes through.
- **Only pages from allowed origins can connect.** That stops another website from opening a connection in a visitor's browser.

## Bug found and fixed

Shutting the server down left clients with no close status, because cancelling a connection's read context makes the WebSocket library drop it without a reason. The server now tracks live connections and closes each with "going away".

## Checks

- `internal/syncsvc` and `internal/gateway`: all tests pass under the race detector. They include 10 concurrent writers on one document, idle unload and reload, a late joiner getting history, a foreign origin refused, and a failing backend.
